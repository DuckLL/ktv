# 單人練唱優化與參考分析

## 參考版本

分析 [KAREOKIE v0.1.4 的公開安裝檔](https://github.com/a8594755-maker/KAREOKIE-releases/releases/tag/v0.1.4)，以靜態方式解開 NSIS、內層 7z。程式使用 Electron，安裝包直接附帶 Python 後端原始檔；本次未執行該 Windows 程式。安裝檔 SHA-256：

`6e7f9c102996c1c776e50f68edfd7ffce454942803473f1f21a2a8353adcea52`

相關模組為 `pitch_extractor.py`、`scorer_ai.py`、`lyrics_aligner.py` 及前端音訊處理程式。以下記錄設計觀察與本專案的實作取捨，不收錄第三方程式碼。

## 可借鏡的設計

- 音高處理分成原始 F0、可信人聲區域、局部八度誤判修正、平滑及穩定音符分段。原始逐格分析不直接當作練習用音符。
- 音符的穩定中段比起音、收尾更適合評估；比對保留時間容錯，顫音不應直接變成錯音。收音太少時不給分。
- 歌詞先從多個來源取得候選，再比對歌名、歌手與版本；完整對齊以分離後人聲的 Whisper 轉錄與文字匹配完成。此流程的資源需求明顯高於搜尋既有 LRC。
- 觀察到的音高穩定主要依據局部旋律與持續時間。將所有起音強制放在固定拍點會改變真實演唱，不適合作為音準判定基準。

## KTV 的實作

保留 SwiftF0 與瀏覽器 Pitchy。後端對原有 `pitch.json` 加入獨立後處理，產生 `practice_pitch.json`：

1. 修正兩側旋律一致、短於 180 ms 的返回式八度誤判；持續的真正八度跳音保留。
2. 排除極短雜訊，於連續有聲區間內做短窗中位數平滑；休止不補成有效音高。
3. 用持續的音高變化建立音符區段，顯示容錯帶。
4. 由伴奏的頻譜起音估計拍點，週期性不足則省略。拍線是參考，音高與歌詞仍使用歌曲實際時間。

快取依原始音高、伴奏修改時間及分析版本重建；不更動原始音高資料、不需重跑 Demucs。第一次建立練唱快取會多一次輕量的伴奏解碼與節拍分析。

麥克風的大跳音需由連續訊號確認，判斷獨立於目標音高，避免把錯音自動修成正確答案。預設音準容許 ±80 音分、時間容許 120 ms，另有寬鬆及精準設定；低八度演唱仍由使用者明確選擇。時間比對會補償瀏覽器回報的輸出延遲，再疊加手動收音延遲校正。設定只存於瀏覽器，聲音仍不會上傳或儲存。

首次播放自動清理影片歌名、搜尋 LRCLIB，依歌名、歌手、長度與版本標記判斷能否自動選用。現場、翻唱、混音等版本不混選；不確定時只顯示候選，已保存的選擇優先。多句人聲起音能支持同一個時間差時才自動校正；無法判斷時保留 LRC，提供逐句編輯並保存。這是保守的同步歌詞校正，不是純文字歌詞的語音強制對齊。

## 驗證與限制

合成訊號涵蓋短八度誤判、持續的大跳音、顫音、休止、輕聲、靜音、輸出延遲、時間容錯與歌詞校正方向。瀏覽器流程涵蓋搜尋加入歌曲、自動選詞、還原已選版本、逐句時間保存、收音啟用、設定記憶及 390／320 px 手機寬度。

首次改善原有〈七里香〉快取時，相鄰有效格超過 7 半音的跳動由 21 次降至 3 次。這只量化尖峰減少，不能視為音高正確率；合聲、真實大跳音、MV 對白與人聲分離殘留仍可能影響目標。節拍可能有倍速／半速歧義或隨速度變動失準，因此不參與修改音符時間，也不拿來直接扣分。

專案預設測試為 Python 64 項通過、1 項略過（主機未安裝 FFmpeg），JavaScript 12 組通過。額外下載的靜態 FFmpeg 7.0.2 能執行音訊測試，但既有 −6 key 的硬切尾音測試量到約 46 ms 的尾音，比原有 40 ms 容許值稍長。將 `HEAD`（`00af34f`）的轉調程式與測試獨立取出後也重現相同的 46 ms 結果，確認不是本次修改的回歸；保留原本轉調程式與測試，未放寬測試標準。

## 瀏覽器 Review

2026-10-25 以 Chromium 實際呼叫 YouTube 與 LRCLIB：搜尋取得 8 個結果、開啟既有〈七里香〉、自動選用周杰倫版本並顯示 36 句歌詞，驗證音訊播放、跳轉與逐句導航；音高介面取得 509 個音符區段及 360 個估計拍點。桌面與手機均無 JavaScript 例外或失敗的 HTTP 回應。媒體和資料庫使用獨立暫存複本。

另建立可重複執行的 [瀏覽器回歸測試](../tests/browser/README.md)，經 Chromium 麥克風輸入已知 A4 訊號並確認音準回饋。Review 發現並修正快速選詞的儲存競態：新版本的文字、時間差準備完成後才一併切換；不同版本的延遲儲存分別保留，同一類寫入依序完成。測試涵蓋等待新版本回應時修改舊版本，以及快速分別調整兩版時間差。
